Ethereum · Transaction evidence

A transaction hash
is not a payment receipt.

The wallet has a hash. The recipient has no payment. Both observations can be true.

Severian Roth · 9 September 2026

Imagine a payment screen that displays a transaction hash and then loses its connection. It is tempting to show either “Paid” or “Failed.” The first label assumes too much about the network. The second assumes too much about the connection failure.

The useful question is narrower: what evidence did the application actually receive? Ethereum exposes several stages, and each supports a different statement.

A hash identifies an attempt

Signing authorizes a particular transaction. Broadcasting sends it to a node for propagation. Inclusion places it in a block. These are separate steps in Ethereum’s transaction lifecycle. A hash can identify a signed transaction before there is any block containing it.

That distinction matters even when the wallet successfully receives a response from its RPC provider, the service through which it talks to a node. A submission response is useful tracking evidence. It is not a statement that the requested transfer has executed.

Ask for the execution receipt

The eth_getTransactionReceipt method returns a receipt when one is available, or null when none is found. Pending transactions do not yet have receipts. A null result therefore does not establish that the payment failed.

A receipt adds the block number, block hash and execution status. EIP-658 defines that status for transactions after the Byzantium upgrade: zero means the top-level execution failed; one means it succeeded. In JSON-RPC responses those values appear as 0x0 and 0x1.

“Included” and “succeeded” answer different questions. A failed execution can still be recorded in a block. The presence of a receipt alone is insufficient evidence for a green payment badge.

Evidence available to the application
ObservationWhat it establishes
Transaction hashAn identifier to investigate; inclusion is unconfirmed.
Receipt is nullThis endpoint returned no receipt.
Receipt status 0x0Execution failed in the reported block.
Receipt status 0x1Top-level execution succeeded in the reported block.

Execution success still needs interpretation

The status bit does not describe the customer’s intention. A contract call may complete successfully while doing something other than the transfer the interface meant to request. The ERC-20 standard, for example, requires callers to handle a false return value from token methods rather than assuming every call succeeds.

A payment system therefore needs a check specific to the action: the correct network, intended asset, recipient and amount, supported by the relevant transaction data and contract events or state. “The call did not revert” and “this invoice was paid” are different claims.

Finality is another question

Even a successful receipt describes inclusion in a particular block. Ethereum’s consensus finality provides a stronger commitment to that history. An application should say which stage it requires before treating a payment as settled.

This is about Ethereum’s base layer. A rollup’s sequencing, settlement and withdrawal stages need their own explanation; borrowing the word “confirmed” does not make their guarantees identical.

Keep a connection error separate

Return to the frozen screen. A timeout describes the application’s ability to obtain a response. It does not report the transaction’s execution status. My design recommendation is to preserve the attempt’s network and hash, show that the outcome is still being checked, and reconcile that attempt before offering a fresh payment.

The wording is part of the behavior. A button labelled “Try again” can invite another payment; “Check this transaction” asks for evidence about the existing one. The system should know which action it is performing before asking the user to click.
